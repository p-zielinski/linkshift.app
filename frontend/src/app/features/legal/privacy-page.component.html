Information we collect

  • Account data: email, organization name, and whether you are the organization owner.

  • Authentication flow tokens: token hashes stored in Redis for about 30 minutes for email verification, password reset, and similar flows.
  • Organization invites: email addresses of people you invite to your organization, token hashes, and expiry (invite links expire after about 30 minutes).
  • Organization membership visibility: when you belong to an organization, other members of the same organization can see your email address and role (owner or member) in the Organization area of the dashboard. Organization owners can also see whether your email is verified and whether your account is blocked.
  • API keys: key name, token hash (not the full secret), token prefix, and last-used timestamp.
  • Configuration data: domains, redirect rules, link maps, and settings you create.
  • Redirect tests: saved simulation inputs and expected results you store in the Service, which may optionally include an IP address, User-Agent, hostname, request headers, and query parameters you choose to save in redirect test fixtures.
  • Redirect traffic analytics: aggregated request method, path, query, destination, and link-map keys from live redirects (visitor IP addresses are not stored in the analytics database).
  • Public tools usage: URLs you submit to the QR code generator and redirect trace tools (redirect trace sends server-side HTTP requests to those URLs; destination hosts may see our infrastructure IP), queries to our read-only documentation MCP endpoint, and an optional User-Agent header when you use redirect trace. QR URLs are processed transiently on the server and are not stored. Redirect trace URLs may appear in short-lived operational logs. Operational logs for QR generation record your IP address only (not the URL); redirect trace logs may record your IP address, the traced URL, and an optional User-Agent header.
  • Usage data: service events and timestamps from application and security logs (for example, request metadata, errors, and operational events) for security and reliability — not for marketing profiling.
  • Billing data: Paddle acts as merchant of record and is an independent controller for payment data (card details, tax, and invoicing). We store subscription status, Paddle identifiers, and checkout session records (plan, session status, and metadata).
  • Legal acceptance records: confirmation that you accepted the Terms of Service and this Privacy Policy, minimum-age confirmation, version identifier, and timestamps.
  • Identity verification documents if we request know-your-customer (KYC) checks under our Terms of Service.
  • Documentation assistant: questions you submit, generated answers, optional feedback ratings, timing or token-usage metadata, and conversation summaries (hidden thread context from prior turns) when you use this feature in the Service (for example, on our documentation or while signed in). Conversation summaries may be sent to our API and to OpenAI to generate answers when you ask follow-up questions. We do not share this data with OpenAI for model training. Your IP address may be used briefly for rate limiting (stored in Redis for about one minute) and may appear in short-lived operational logs (up to approximately 96 hours). Questions, answers, and ratings are stored in Supabase when that logging is configured.
  • Browser-local data: a cache of your signed-in profile and organization details, interface preferences, and onboarding state stored on your device to load the dashboard faster and remember your choices.

We do not host your websites, applications, or content; we only store configuration data and service logs needed to deliver the Service.

Browser storage

The Service uses your browser's local storage and session storage (technologies similar to cookies) to operate the dashboard and documentation. Most data stays on your device until you clear browser data manually. Signing out removes only the account cache; other local and session data (documentation history, Try Me drafts, interface preferences) persists until you clear it in the UI or clear browser data.

Access tokens for authenticated API requests are held in memory only and are not stored in local storage.

  • Account cache (local storage): a copy of your signed-in profile and organization details under user_data and organization_data (such as email and organization name) so the app can load faster after refresh. Removed when you sign out.
  • Interface preferences (local storage): dashboard mode (linkshift-dashboard-mode), selected domain group (linkshift-active-domain-group), and onboarding or setup checklist progress (such as dashboard-onboarding-confirmed and linkshift-setup-checklist).
  • Documentation assistant history (local storage): recent chats on your device under linkshift_docs_assistant_history_v1. See Documentation assistant below.
  • Documentation Try Me (session storage): an API key (linkshift.docs.tryMe.apiKey) and request drafts (linkshift.docs.tryMe.drafts.v1) for the current browser tab session. The key is sent to our servers only when you run a Try Me request.
  • OpenAPI spec cache (session storage): a cached copy of the API specification under the key linkshift.docs.openapi.v1 for the current browser tab session.

Visitor IP addresses

We do not store visitor IP addresses in the redirect analytics database, and we do not use IP addresses for marketing or profiling.

IP addresses may be processed temporarily for limited technical purposes:

  • Rate limiting and abuse prevention (Redis counters, typically seconds to about two hours for login abuse protection).
  • Operational logs (Loki, retained for approximately 96 hours) for security monitoring and incident response.
  • Cloudflare Turnstile bot protection when you sign in, register, request a password reset, accept a team invite, or use the documentation assistant (Ask docs).
  • Optional {{ '{' }}ip{{ '}' }} placeholder substitution in customer-configured redirect destinations (your responsibility for third-party destinations you configure).
  • Public tools — QR code generator: your IP address may appear in operational logs. URLs are processed server-side but are not stored in operational logs for QR generation.
  • Public tools — Redirect trace: your IP address, the traced URL, and an optional User-Agent header may appear in operational logs. Redirect trace issues outbound HTTP requests from our servers to the URLs you submit.
  • Public tools — Documentation MCP: your IP address may appear in operational logs for read-only documentation queries. We do not store MCP conversation content (unlike the documentation assistant).

Redirect traffic and analytics

When visitors hit your live redirect rules, we record aggregated analytics in hourly buckets to power dashboard reports. Stored fields include request method, path, query parameters, destination, link-map keys, and related breakdown dimensions (for example, RedirectRuleHitBreakdownHourly aggregates).

Analytics data is kept for a limited period that depends on your subscription plan. Current retention limits are listed on our Pricing page and shown in the Service (for example, Click data retention on your analytics dashboard). We may update plan limits from time to time with reasonable notice; the period that applies to your account is the one displayed in the Service for your plan. Data is aggregated; individual visitor IP addresses are not stored in the analytics database.

Public tools

We offer public tools that do not require an account: a QR code generator, a redirect trace tester, and a documentation MCP endpoint for read-only documentation access in compatible clients. These tools are subject to per-IP rate limits.

The documentation MCP endpoint provides read-only access to our documentation catalog. Your IP address may appear in short-lived operational logs, and we do not store MCP conversation content or chat logs.

URLs you submit are processed server-side to generate QR codes or trace redirect chains. The redirect trace tool sends server-side HTTP requests to the URLs you submit; destination servers may log our infrastructure IP address. The traced URL and an optional User-Agent header may appear in short-lived operational logs. For API details and limits, see our Public tools API guide.

Security screening

Destination URLs from your redirect rules and link maps may be submitted to the Google Web Risk API and other automated security screening services to detect malicious or unsafe destinations.

Bot protection (Cloudflare Turnstile)

We use Cloudflare Turnstile on public account flows — sign-in, registration, password reset requests, and team invite acceptance — and on the documentation assistant (Ask docs). Turnstile may run in invisible mode. Cloudflare processes limited technical signals (such as browser and network characteristics) to distinguish humans from bots. Your IP address may be processed as part of this check. For details on the data Cloudflare collects and how it is used, see Cloudflare’s Turnstile Privacy Addendum (which supplements Cloudflare’s main privacy policy).

Automated decisions

Web Risk and other automated security screening may block redirect rules or accounts without human review when destinations are flagged as malicious, unsafe, or high-risk. These decisions can limit access to the Service immediately. See our Terms of Service for enforcement details, including limitations on refunds or credits during security blocks.

Documentation assistant

The documentation assistant lets you ask questions and receive answers drawn from official documentation. You may access it wherever we make it available in the Service (such as our documentation site or signed-in areas of the app). When you submit a question, it is sent to our tools API to generate an answer. We may store the question, answer, sources cited, response time, and an optional helpful/not helpful rating to improve quality and prevent abuse.

When Supabase logging is enabled, these records are stored in the agent_search_logs table in Supabase, hosted in the European Union. IP addresses are not stored in that database — only the question, answer, sources, rating, timing, and token usage metadata. IP addresses may still be used briefly for rate limiting or appear in short-lived operational logs as described above.

Even when Supabase logging is not configured, your questions and conversation summaries sent for follow-up context are still sent to OpenAI to generate responses. We configure the API so OpenAI does not use this content for model training.

Recent chats can be saved in your browser’s local storage on your device so you can return to them later. You can clear that history in the assistant UI; clearing it does not delete server logs already recorded for earlier questions.

Conversation summaries (conversationSummary) are stored locally as part of your chat history on your device. When you ask a follow-up question, the summary may be sent to our API and to OpenAI to provide context for the next answer. Conversation summaries are not stored in Supabase.

Bot protection for this feature uses Cloudflare Turnstile — see Bot protection (Cloudflare Turnstile) above.

The documentation assistant uses OpenAI as a subprocessor to generate answers from retrieved documentation context. When you submit a question, your question and any conversation summary sent for follow-up context are transmitted to OpenAI for answer generation only. We use API settings that opt out of using your content for model training. Do not submit sensitive, confidential, or proprietary information, protected health information, or personal data of children through the documentation assistant. For how OpenAI handles API data, see OpenAI API data usage policies.
